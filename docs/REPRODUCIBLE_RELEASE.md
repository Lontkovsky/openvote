# Reproducible client release and independent monitor

Status: development self-verification for [V024](https://github.com/Lontkovsky/openvote/issues/35). The provenance is generated by this repository and is not a signed third-party attestation.

## Defined release artifacts

The reproducibility boundary contains both browser clients:

- `full/`: every HTML, JavaScript, CSS, WebAssembly, cryptographic client asset and license delivered by the full test platform;
- `demand/`: every HTML, JavaScript, CSS, media, cryptographic client asset and license delivered by the demand landing.

No executable file inside those directories is excluded from byte comparison. Docker filesystem metadata, the server runtime image and native Belenios binaries are not claimed reproducible by this client check. The pinned crypto image is an input: its exact image ID and the hashes of the four injected client files are recorded in provenance.

## Baseline

Before the release process existed, two consecutive builds in the same workspace were byte-identical: seven full-client files shared tree SHA-256 `a5858d5df5b23f0c6f3ae4e2983da2c117ebe403c3790acbb2ee9bbc75b83abf`; nine demand-client files shared `4a7e32e6e26ea93f8d8f0e90901b4e00a8b7504f62cc8c9f66482027d591b6b6`. That established deterministic Vite output only. It did not use fresh dependency directories and produced no release manifest, SBOM, provenance or independent monitor.

## Exact release verification

Use Node 24.20.0 and pnpm 10.33.0 from a clean committed checkout. Build the pinned crypto input, then create a new output directory:

```sh
docker build --platform linux/amd64 --target crypto-runtime -f infra/crypto.Dockerfile -t openvote-crypto:3.3.0 .
pnpm install --frozen-lockfile
pnpm release:verify .runtime/release
```

The command refuses tracked changes and an existing output path. It copies only the declared tracked client build inputs into two separate temporary source directories, injects the same recorded crypto client input, creates fresh dependency directories with the frozen lockfile, builds full and demand clients in each directory and compares every resulting byte. A difference fails with `REPRODUCIBLE_BUILD_MISMATCH` and creates no release output.

A successful directory contains:

- the exact `full/` and `demand/` artifacts from the first clean build;
- strict `full-client-manifest.json` and `demand-client-manifest.json` files binding URL path, artifact path, byte length and SHA-256 to the source commit;
- `sbom.cdx.json`, a deterministic CycloneDX 1.6 inventory of resolved workspace dependencies plus Belenios and libsodium;
- `provenance.json` with repository commit/time, Belenios commit, Node/pnpm/Vite versions, platform, crypto image ID, every declared source/crypto input hash and both tree hashes;
- `SHA256SUMS` for every released file and metadata document.

The exact-head CI performs the same two-clean-build comparison and uploads the result as `release-public-evidence`. The CI result remains a repository-controlled self-check; it is not an independent build attestation or a signed release.

## Independent client monitor

Keep a trusted client manifest outside the site being checked. The monitor reads only that local file and downloaded bytes:

```sh
pnpm client:monitor .runtime/release/demand-client-manifest.json https://openvote.com.ua
```

It requires HTTPS except for loopback tests, follows no redirects, sends no credentials or referrer, applies a ten-second timeout and refuses a body larger or smaller than the trusted length. It downloads every manifest path and checks the exact SHA-256. The focused HTTP test first verifies the trusted HTML/JavaScript pair, then substitutes the server JavaScript and receives `CLIENT_ARTIFACT_MISMATCH`.

The monitor must run from infrastructure and a manifest controlled separately from the checked web host. A check loaded from the same compromised host is not independent. Even an external monitor proves only what that monitor received at that time; a host or network capable of selective delivery may show other users different bytes. Multiple independently operated monitors and evidence exchange remain production-readiness work.

## Active-poll update rule

Do not silently replace the trusted voting client during an active poll. An emergency client change requires a new source commit, new manifests/checksums/SBOM/provenance, an incident record describing the reason and affected poll window, and a fresh external monitor baseline. Whether an affected result remains valid is an explicit incident decision; the release tooling does not silently rewrite or approve it.
